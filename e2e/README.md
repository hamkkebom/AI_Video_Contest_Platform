# E2E 테스트

## 무엇을 담는가

`regressions.spec.ts` 는 **실제로 운영에서 깨졌던 것들**만 담는다. 추측으로 쓴 테스트가
아니라 사고 목록이며, 각 테스트에 어떤 사고였는지 주석으로 남긴다.

새 항목을 추가하는 기준: **한 번이라도 운영에서 터졌거나, 터지면 조용히 지나갈 것.**
"이 버튼이 파란색인가" 같은 것은 넣지 않는다.

## 실행

```bash
bun run test:e2e          # 로컬 dev 서버 (없으면 자동 기동)
bun run test:e2e:prod     # 운영 사이트 대상
```

`npx playwright` 는 쓰지 말 것. bun 설치 환경에서 `.bin/playwright` 가 만들어지지 않아
`npx` 가 다른 버전을 받아오고, "두 개의 @playwright/test" 오류로 테스트를 못 찾는다.
위 스크립트는 로컬 CLI 를 직접 가리킨다.

브라우저가 없다는 오류가 나면:

```bash
node node_modules/@playwright/test/cli.js install chromium
```

## 원칙

**상태를 바꾸지 않는다.** 운영 DB 를 함께 보므로 제출·승인·삭제 같은 쓰기는 넣지 않는다.
쓰기 경로는 "비인증이 거부되는가"까지만 확인한다.

**빈 목록과 장애를 구분한다.** 목록 페이지는 200 만 보지 말고 항목이 실제로 있는지 센다.
articles 사고가 "아티클이 없습니다"로 위장됐던 것이 이 테스트들이 생긴 이유다.

## 로그인이 필요한 흐름

출품 제출, 관리자 승인 등은 아직 덮지 못했다. 계정이 필요한데 운영 DB 에 테스트 계정을
만드는 것은 별개 결정이라 미뤘다. 붙일 때는 `storageState` 로 로그인 세션을 저장해
재사용하고, 쓰기가 일어나므로 **전용 스테이징 프로젝트**를 먼저 두는 편이 낫다.
