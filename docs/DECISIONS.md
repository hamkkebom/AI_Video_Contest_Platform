## D-014 · 주최자를 1급 개념으로 노출 + companies 익명 차단 (2026-08-01)

- **배경**: 로드맵 후보 C(멀티테넌트 SaaS) 방향이 정해지면서 주최자를 공개해야 했는데, 코드는 주최자를 단일 테넌트로 가정하고 있었다. 공모전 상세의 주최 표기가 `isAdminHost ? '함께봄 주식회사' : hostUser.name` 으로 **하드코딩**돼 있어 외부 주최자의 공모전도 운영사 이름으로 표시됐고, `contests.host_company_id` 는 어디서도 읽히지 않았다. 더 큰 문제로, **042(D-009)가 `companies`·`company_members` 를 빠뜨려** 두 테이블이 아직 `FOR SELECT USING (true)` + anon SELECT 권한 상태였다. 사업자등록번호·대표자명·주소·연락처·사업자등록증 이미지 URL과 소속 관계가 anon 키로 열려 있었고, 인증 검사가 없는 `/api/admin/companies/[id]` 가 미들웨어 보호 밖(`/api/admin/*` 은 `/admin` 으로 시작하지 않는다)에 있어 그대로 반환됐다. 확인 결과 기업 데이터가 0건이라 실제 유출은 없었다 — 외부 주최자를 받기 직전이 마지막 차단 시점이었다.
- **결정**: 042와 같은 패턴으로 `public_companies` 뷰(id·name·logo_url·website·description, `status='approved'` 한정)를 만들고 원본 테이블의 anon SELECT 를 회수했다. `company_members` 는 본인·같은 회사·관리자만 조회한다(자기 참조 재귀를 피하려 `is_company_member()` SECURITY DEFINER 함수 사용). 주최 표기는 **등록 기업 → 플랫폼 자체 개최(admin) → 주최 담당자** 순으로 해석하고, 공개 주최자 페이지 `/hosts/[id]` 를 신설했다. Event JSON-LD 의 organizer 도 플랫폼 고정에서 실제 주최자로 바꿨다. (마이그레이션 048)
- **결과**: 주최자가 공개 화면에 존재하게 됐고 사업자 정보는 뷰 밖으로 나갈 수 없다. 부수 발견 — `/hosts` 도입으로 `pathname.startsWith('/host')` 가 공개 주최자 페이지까지 로그인으로 보내는 접두사 충돌이 드러나, 미들웨어·헤더·푸터의 경로 비교를 세그먼트 경계(`isUnder`)로 교정했다. 인증 없는 관리자 API 는 `/api/admin/companies/[id]` 하나만 실제 구멍이었고(나머지 4개는 RLS 가 쓰기를 막고 있었다) 명시적 관리자 확인을 추가했다.

## D-015 · 주최자 온보딩은 좁은 RPC 두 개로 (2026-08-01)

- **배경**: 멀티테넌트(D-014)의 다음 조각은 외부 주최자가 스스로 기업을 등록하는 흐름인데, RLS 구조가 셀프서비스를 막고 있었다 — ① `company_members`에 INSERT 정책이 없고, 열면 아무나 임의 회사의 멤버로 자신을 추가할 수 있다(소속 위조). ② 신청 직후에는 아직 멤버가 아니라 companies의 "소속 멤버 조회" 정책에 걸려 `INSERT ... RETURNING`도 실패한다(가입 전엔 자기 회사를 SELECT할 수 없는 순환). ③ profiles는 "본인만 수정"이라 관리자가 승인 시점에 host 역할을 부여할 방법이 없다.
- **결정**: 테이블 쓰기 권한을 여는 대신 검증이 내장된 SECURITY DEFINER RPC 두 개만 연다 — `apply_host_company`(기업 pending + 신청자 owner 멤버십 원자 생성, 중복 신청 차단)와 `admin_set_company_status`(is_admin 강제, 승인 시 owner 전원에게 host 역할 부여). 직접 INSERT 정책은 `status='pending'` 강제로 교체해 우회 승인을 막았다. (마이그레이션 049) 흐름: `/hosts/apply`(로그인 필요) → `/admin/companies` 승인/반려 버튼 → host 대시보드 개방. 진입점은 푸터 "공모전 개최 신청".
- **결과**: 온보딩 코드 완성, RPC 미배포 환경에선 503으로 우아하게 실패. **048·049 마이그레이션은 MCP가 읽기 전용이라 수동 적용 필요** — 적용 전까지 신청 접수 불가.

## D-016 · RLS 접근 규칙 확립, 046의 서술 정정 (2026-08-02)

- **배경**: 같은 성격의 RLS 사고가 세 번 반복됐다. ① D-009(공개 데이터가 원본 테이블로 새던 것) ② 050이 `articles`에 `is_admin()` 정책을 추가해 **공개 스토리 페이지를 망가뜨린 것** ③ `getInquiryCountByStatus`가 `unstable_cache` 때문에 익명 클라이언트를 써서 관리자 대시보드의 "대기 문의"가 **항상 0**이었던 것. ②는 046이 "`TO authenticated`로 한정하면 해결된다"고 적어둔 것을 검증 없이 따르다 발생했다 — 그 서술은 사실이 아니다. 046이 고쳤다는 `inquiries`·`agency_requests`도 지금 익명에게 같은 오류를 반환한다(다만 이 두 테이블은 접수 전용이라 익명이 읽을 이유가 없어 기능상 문제는 없다).
- **결정**: 규칙을 [IA.md](IA.md) §3-9에 명문화했다 — ① 테이블 정책에 `is_admin()`을 넣지 않는다 ② 공개 읽기는 뷰(`public_*`) ③ 관리자 경로는 SECURITY DEFINER RPC(정책 식이 아니므로 `is_admin()` 호출이 안전하고, 바꿀 컬럼을 좁힐 수 있다) ④ `unstable_cache` 안에서는 세션 클라이언트를 못 쓴다 ⑤ 조회 실패를 빈 값으로 삼키지 않는다(`logDataError` 44곳 적용).
- **결과**: 관리자 문의 건수 버그 수정. 046의 잘못된 서술은 이 항목이 정정한다 — **문서보다 실제 동작을 먼저 확인할 것.** 이 세션에서 그러지 않아 운영 페이지를 한 번 망가뜨렸다.

## D-017 · 문의 답변은 이메일 대신 사이트 안에서 (2026-08-02)

- **배경**: 로드맵 1순위가 "이메일 발송"이었는데, 정작 무엇 때문에 필요한지 따져 보니 세 가지였다 — 주최자 승인 통지, 심사위원 초대, 문의 답변. 앞의 둘 중 승인 통지는 **주최자가 이미 계정을 가진 회원**이고, 문의 답변도 **회원 문의라면 마찬가지**다. 즉 통지의 상당 부분은 받는 사람이 이미 로그인할 수 있는 사람이다. 그런데 `inquiries` 에는 **답변을 담을 컬럼 자체가 없어서**, 관리자가 상태를 `resolved` 로 바꿔도 답변 내용은 전화·카톡 등 플랫폼 밖으로 나갔고 문의자는 자기 문의가 어떻게 처리됐는지 사이트에서 확인할 방법이 없었다.
- **결정**: Resend 계정·DNS·도메인 인증이 필요한 이메일 대신 내부 문의함을 먼저 만든다. `inquiries.answer`/`answered_at`/`answered_by` 추가(마이그레이션 053), 관리자 목록에서 답변 작성·수정, 회원은 `/my/inquiries` 에서 열람. 조회 범위는 046 의 "본인만 조회"(`auth.uid() = user_id`) RLS 가 그대로 강제하므로 새 정책을 만들지 않았다 — [IA.md](IA.md) §3-9 ③ 과 달리 RPC 가 필요 없는 이유는 관리자 쓰기 정책(`inquiries: 관리자 처리`)이 046 에 이미 있기 때문이다.
- **결과**: 회원 문의 답변과 주최자 승인 통지는 이메일 없이 닫힌다. **남는 구멍은 두 곳** — ① 비회원 문의(계정이 없어 보여줄 화면이 없다. 관리자 화면에 회신 이메일을 노출해 수동 회신을 유도한다) ② 심사위원 초대(초대 대상이 아직 회원이 아니다. "기존 회원 중에서 지정"으로 설계를 바꾸면 이것도 이메일 없이 닫힌다). 이메일은 보류 유지 — 트리거는 "비회원 문의가 실제로 쌓일 때".

## D-018 · 심사위원은 초대하지 않고 배정한다 (2026-08-02)

- **배경**: 로드맵 2순위였던 "심사위원 초대 실동작화"를 열어 보니 목업 하나가 아니라 세 겹의 문제였다. ① **`judges` 테이블에 SELECT 정책만 있고 INSERT/UPDATE/DELETE 정책이 아예 없다.** 042·046 이 조회 범위를 좁히며 정책을 다시 쓸 때 쓰기 정책은 어느 마이그레이션에도 만들어지지 않았다 — 관리자 공모전 화면의 심사위원 검색·배정 UI 는 멀쩡히 붙어 있는데 DB 가 거부한다(050 의 articles 와 같은 사고). ② `POST /api/judges` 가 `roles ⊇ {admin|host}` 만 확인하고 **그 공모전의 주최자인지는 보지 않았다** — 멀티테넌트에서 아무 주최자나 남의 공모전에 심사위원을 꽂을 수 있다. ③ 배정 시 대상자에게 judge 역할을 줘야 하는데 `profiles` 는 "본인만 수정"이라 그것도 막혀 있다(D-015 가 host 역할에서 겪은 것과 동일). 그리고 `/invite/[token]` 은 가짜 공모전명·가짜 주최자("김호스트", "기업 1")·가짜 초대문을 아무에게나 렌더하고, 수락 버튼이 아무것도 저장하지 않으면서 "심사위원으로 등록되었습니다"라고 표시하는 목업이었다.
- **결정**: 이메일이 없으므로 **초대→수락 2단계를 버리고 배정 1단계로 바꾼다.** 검증이 내장된 SECURITY DEFINER RPC 세 개만 연다(마이그레이션 054) — `assign_contest_judge`(관리자 또는 **그 공모전의** 주최자만, judge 역할 동시 부여), `remove_contest_judge`(같은 소유권 검사 + 이미 채점한 심사위원은 거부, 다른 배정이 없을 때만 역할 회수), `find_member_for_judge`(이메일 **정확 일치**로 1명만 — 주최자에게 회원 명부를 열어 주지 않기 위해 부분 검색을 제공하지 않는다). 주최자 화면의 가짜 "이메일 초대" 상자와 동작하지 않던 "재초대" 버튼은 실제 배정·해제 컨트롤로 교체했고, `/invite/[token]` 은 삭제했다.
- **결과**: 심사위원 배정이 관리자·주최자 양쪽에서 실제로 동작하게 됐고 소유권 구멍이 닫혔다. **대가는 명확하다 — 아직 가입하지 않은 사람은 심사위원으로 세울 수 없다.** 화면이 그 사실을 그대로 말한다("먼저 회원가입을 안내해주세요"). 외부 인사를 이메일로 부르는 흐름이 정말 필요해지면 그때가 이메일 도입 시점이고, 그 전까지 이 설계로 충분하다.

## D-019 · 제출 메가폼 분해 — 복붙이 만든 동작 차이부터 (2026-08-02)

- **배경**: `contests/[id]/submit/page.tsx` 가 2,235줄이고 그중 `handleSubmit` 하나가 685줄이었다. 로드맵은 이걸 "손대기 겁나는 상태"로만 적어 뒀는데, 열어 보니 크기보다 **복붙이 만든 동작 차이**가 실제 문제였다. 영상·썸네일·인증이미지 업로드가 신규/수정/재제출 세 경로에 각각 적혀 있었고, **재제출 경로의 영상 업로드만 약한 버전**이었다 — Cloudflare 처리 대기 폴링도, CORS 로 응답이 잘렸을 때 실제 업로드 성공을 구제하는 로직도, 처리 불가 파일 즉시 실패도 없었다. 즉 같은 파일로 신규 제출은 성공하는데 재제출은 실패할 수 있었다. 부수로, 멈춤 감지 코드가 `uploadProgress`(React state)를 클로저에서 읽어 항상 초기값과 비교하고 있어 **한 번도 발동하지 않았다.**
- **결정**: 업로드 원시 함수를 `_lib/uploads.ts` 로 뽑아 세 경로가 같은 코드를 쓰게 하고(`requestVideoUploadUrl`·`uploadVideoToStream`·`uploadFileToStorage`·`buildStoragePath`), 결과 다이얼로그 3종을 `_components/submit-dialogs.tsx` 로 분리했다. 진행률은 상태를 넘기지 않고 콜백으로 받는다. 멈춤 감지는 모듈 안에서 진행률을 직접 들고 있게 고쳤다.
- **결과**: page.tsx 2,235 → 1,688줄, 재제출이 신규 제출과 같은 견고한 경로를 타게 됐다. 관리자 공모전 폼(2,463줄)도 같은 방식으로 순수 부분(`contest-form-helpers.ts`, 폼 타입·팩토리·포맷·업로드·영상 썸네일 추출)을 떼어 2,166줄로 줄였다. 두 곳 모두 **남은 것은 폼 JSX** — 크기 문제일 뿐 동작 차이가 없어 뒤로 미뤘다. 공모전 폼 업로드는 출품 제출 업로드와 닮았지만 합치지 않았다: 이쪽은 `x-upsert=true`·10분 타임아웃·서버 원문 오류 노출이 필요하고(관리자가 읽는다) 저쪽은 그 반대다. 운영 DB 라 제출 흐름을 실제로 돌려 볼 수 없었고 타입체크·빌드까지만 확인했다.

## D-020 · 대시보드는 합치지 않고 서로 잇는다 (2026-08-02)

- **배경**: `/my`·`/judging`·`/host`·`/admin` 이 서로를 전혀 모르는 네 개의 사이드바였다. 심사위원으로 배정되면 judge 역할이 붙지만(D-018) `/my` 안에는 `/judging` 으로 갈 링크가 없어 헤더 드롭다운으로 되돌아가야 했다 — 최초 지적("미로 같다")의 전형이다. 더 나쁜 건 `RoleGuard` 가 **admin 을 특별 취급하지 않는다**는 점이었다. `/host` 는 `allowedRoles={['host']}` 라서, host 역할이 없는 관리자가 헤더가 안내하는 "주최자 대시보드"를 누르면 홈으로 튕겨 나갔다. 문서(AGENTS.md·IA.md §4)는 "admin 은 전체 접근"이라고 적혀 있었지만 코드가 그렇지 않았다.
- **결정**: 라우트를 옮기는 통폐합(리다이렉트·링크 전수 수정이 따라온다)은 하지 않는다. 대신 ① `RoleGuard` 가 admin 을 전 영역 통과시키게 하고 ② `useOtherDashboards(current)` 훅이 "이 사용자가 들어갈 수 있는 다른 대시보드"만 골라 사이드바 하단 **다른 대시보드** 섹션으로 붙인다. 역할이 하나뿐인 대다수 사용자에게는 아무것도 늘어나지 않는다(빈 목록 → 섹션 없음). `/judging` 가드에서 중복이던 `'admin'` 은 제거했다 — 이제 RoleGuard 가 처리한다.
- **결과**: URL 은 하나도 바뀌지 않았고 죽은 링크가 사라졌다. 겸직 사용자가 대시보드 사이를 사이드바 안에서 이동한다. 로그인이 필요한 화면이라 브라우저로 직접 확인하지는 못했고 타입체크·빌드까지 확인했다.

## D-021 · 이메일은 계정이 없는 상대에게만 (2026-08-02)

- **배경**: 로드맵은 이메일을 "Resend 계정 + aikkumhub.com DNS 레코드 필요"라며 막힌 항목으로 뒀는데, 도메인 문제로 가비아 DNS를 열어 보니 **DKIM(`resend._domainkey`)·SPF(`send` TXT)·MX(`send` → `feedback-smtp.ap-northeast-1.amazonses.com`)가 이미 등록돼 있었다.** 즉 선행 조건이 이미 충족된 상태였고 로드맵 서술이 틀렸다. 반면 `RESEND_API_KEY` 는 로컬·저장소·Vercel 환경변수 어디에도 없다 — **DNS는 됐고 키만 없다.**
- **결정**: SDK 없이 Resend REST 를 fetch 로 호출하는 `lib/email` 을 만들고, **적용 범위를 "계정이 없는 상대"로 한정**한다. 회원 통지는 D-017의 내부 문의함이 이미 처리하므로 메일을 중복으로 보내지 않는다. 첫 사용처는 비회원 문의 답변(로드맵 1-1). 키가 없으면 **던지지 않고 조용히 건너뛴다** — 발송 실패가 답변 저장을 되돌리면 관리자가 쓴 글을 잃기 때문이다. 대신 API가 `delivery: 'email' | 'in_app' | 'failed'` 를 돌려주고 관리자 화면이 그대로 표시한다.
- **결과**: 키만 넣으면 즉시 동작한다. 키가 없는 동안에는 문의 목록 상단에 "비회원 문의 N건에 답변 메일을 보낼 수 없습니다"가 뜨고, 답변 저장 후에도 "직접 회신해 주세요" 경고가 남는다 — **조용히 성공한 척하지 않는다.** 실제 발송은 키가 없어 검증하지 못했고 타입체크·빌드까지만 확인했다.

## D-022 · 심사위원 초대를 되살리되, 토큰만으로는 못 되게 (2026-08-03)

- **배경**: D-018 은 메일이 없다는 전제에서 초대를 버리고 배정만 남겼고, 그 대가로 "가입한 회원만 심사위원이 될 수 있다"는 제약이 생겼다(로드맵 2-1). 발송이 실제로 동작하게 되면서(D-021) 제약을 풀 수 있게 됐다. 다만 되살리는 대상은 **삭제한 목업의 흐름이 아니다** — 그건 가짜 데이터를 렌더하고 수락 버튼이 아무것도 저장하지 않았다.
- **결정**: `judge_invites` 테이블 + RPC 세 개(마이그레이션 055). 판단이 갈린 지점은 셋이다 — ① **토큰을 초대한 이메일에 묶는다.** 링크가 전달돼도 그 주소로 가입한 계정만 수락할 수 있다. 심사위원은 수상 결과에 영향을 주므로 링크 하나로 아무나 되게 둘 수 없다. ② **14일 만료.** 살아 있는 오래된 링크 자체가 구멍이다. ③ **메일을 못 보내는 상태면 초대를 만들지 않는다**(503). 링크를 전달할 방법이 없는 초대는 주최자에게 "보냈다"는 착각만 남긴다. 수락 화면 `/judge-invite/[token]` 은 로그인을 요구하지 않는다(계정이 없는 사람이 여는 화면이므로). 없는 토큰은 404 로 답한다 — "만료됐다"고 알려주면 토큰 유효성을 떠볼 수 있다.
- **결과**: 주최자 화면에서 이메일을 조회했을 때 미가입자면 막다른 길("먼저 회원가입을 안내해주세요") 대신 초대 버튼이 뜬다. 054 의 배정 경로는 그대로 두고 갈래만 하나 늘렸다. **⚠️ 마이그레이션 055 수동 적용 필요.** 실제 초대 메일 수신·수락은 주최자 계정과 미가입 주소가 필요해 검증하지 못했고 타입체크·빌드까지만 확인했다.

## D-023 · 조회수는 표시와 채점을 나눈다 (2026-08-03)

- **배경**: 로드맵 4번이 "익명 조회수 점수 정책"으로 남아 있었다. 열어 보니 026 의 `rpc_record_view` 는 이미 방어가 두껍다 — IP당 분당 60회 레이트리밋, 6시간 중복 제거, 5분 스파이크·누적 이상 플래그. 그럼에도 **비로그인 조회는 `ip_hash` 로 식별**되므로 IP를 바꿔 가며 부풀리는 것을 원천 차단하지는 못한다.
- **결정**: 표시와 채점을 나눈다. 화면의 조회수(`submissions.views`)는 그대로 둔다 — 틀려도 순위가 바뀌지 않는다. 대신 `online_vote_type` 에 views 가 들어간 공모전의 **결과 계산만** `contest_authenticated_view_counts` RPC(마이그레이션 056)로 **로그인 조회를 다시 센다.** 관리자 폼에서 조회수를 고르면 "점수에는 로그인 조회만 반영된다"고 그 자리에서 알린다.
- **결과**: 조회수가 상금을 가르는 값이 되는 경우에만 엄격해진다. 기존 데이터는 영향이 없다 — 지금 있는 공모전은 `online_vote_type='likes'` 다. **⚠️ 마이그레이션 056 수동 적용 필요.**

## D-024 · 아리랑 마이크로사이트는 아리랑에만 (2026-08-03)

- **배경**: `/contests/[id]/landing` 이 **id 와 무관하게** `<ArirangLandingClient />` 를 렌더하고 있었다. 헐버트·채보 130주년·전용 카피가 하드코딩된 컴포넌트라, 제2회를 열면 그 공모전 URL 에서 남의 이야기가 나온다. 게다가 `contests.has_landing_page` 는 저장만 되고 이 라우트에서 읽히지 않았고, 없는 공모전도 랜딩은 200 을 돌려줬다.
- **결정**: 라우트를 "아리랑 전용 마이크로사이트 하나"로 못 박는다. 없는 공모전·draft 는 404(상세와 같은 기준, D-013), 아리랑이 아닌 공모전은 상세로 리다이렉트한다 — canonical 이 이미 상세를 가리키므로 방향이 같다. 판별은 `isArirangContest(id, contest)` 한 곳으로 모았다(id=3 또는 제목에 '아리랑').
- **결과**: 제2회를 열어도 엉뚱한 랜딩이 뜨지 않는다. 공모전별 랜딩이 실제로 필요해지면 그때 이 게이트 안에서 분기하면 된다.

## D-025 · 팔지 않는 것에 가격을 붙이지 않는다 (2026-08-03)

- **배경**: 수익화는 D-005 로 동결인데 `/pricing` 은 DB 가 비면 **9,900원·29,900원 같은 지어낸 가격**을 폴백으로 렌더했다. FAQ 에는 "구독 후 7일 이내 전액 환불" 같은, 팔지도 않는 상품의 약속이 적혀 있었다. 반대로 DB 에 플랜이 있어도 탭에 맞는 게 없으면 `return null` 이라 **페이지가 통째로 빈 화면**이 됐다.
- **결정**: 폴백 가격을 지운다. 플랜이 없으면 "아직 판매 중인 요금제가 없습니다 — 참가·출품·갤러리는 무료"라고 말한다. FAQ 는 지금 사실인 것만 남긴다(결제 불필요, 복수 역할 가능, 개최는 개별 협의).
- **결과**: noindex·sitemap 제외는 그대로 두되(D-005), 들어온 사람에게 거짓말은 하지 않는다. 유료화 재개 시 FAQ 와 가격을 함께 채우면 된다.
